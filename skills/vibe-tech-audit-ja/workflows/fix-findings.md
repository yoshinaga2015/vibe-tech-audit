# Workflow: fix-findings

監査で出た finding を、ユーザー明示のうえ修正する。

## Entry（Safety Gate）

次をすべて満たすこと。欠けたら監査モードへ戻す。

1. ユーザーが修正を明示している（「直して」「fix」「CRITICAL を修正」等）
2. 対象 finding の一覧がある（直前レポートまたはユーザー指定 id）
3. 範囲が分かる（例: CRITICAL のみ / F-003 のみ / 全部）

範囲が曖昧なら推測せずユーザーに1回確認する。**推測でリポジトリ全体をリファクタしない。**

## Phase X1 — 対象確定

入口: ゲート通過。  
行動:

1. 直す finding id と Severity を列挙する。
2. CRITICAL → HIGH →（明示時のみ）MEDIUM の順。LOW は明示時のみ。
3. 各 finding の証拠箇所を再 Read する。

出口: 修正キュー。

## Phase X2 — 最小修正

入口: キュー確定。  
行動:

1. finding ごとに最小の修正を入れる。無関係なリファクタ・フォーマット変更を混ぜない。
2. 認可修正の原則: セッション由来の userId/orgId をクエリに含める。クライアント入力の role/tenant/price を信用しない。
3. 秘密露出: クライアントから除去し、**ローテーションが必要ならユーザーに「鍵を回せ」と明示**（エージェントが本番鍵を勝手に無効化しない）。
4. 1 finding 直したら、その確認手順をもう一度満たすか検証する（検索または論理確認）。

出口: 修正済みファイルと、finding ごとの検証メモ。

## Phase X3 — 再監査（狭い）

入口: キュー消化。  
行動:

1. 直した項目だけ再チェックする。
2. 新規に持ち込んだ問題（認可忘れ、秘密の移設ミス）が無いか機械スキャンを差分に再実行。
3. レポートを更新: status を `open` → `fixed`、検証証拠を追記。
4. 元の監査が `lens = adversarial` なら、影響を受ける攻撃チェーンだけ再実行し、
   `BLOCKED` になったことを確認する。
5. 重大 finding では
   [detection-response.md](../references/detection-response.md) の該当する
   検知／封じ込めコントロールも確認する。

出口: 更新レポート。残 open があれば列挙。

## Phase X4 — 報告

行動:

- 直したもの / 残したもの / ユーザー作業（鍵ローテ、RLS ダッシュボード操作等）を分ける
- コミットはユーザーが求めたときだけ（静止して確認）

## Exit

- 依頼範囲外を変えていない
- 各 fixed に再検証メモがある
- 秘密ローテ等の人手作業を押しつけていない（明示して渡す）
